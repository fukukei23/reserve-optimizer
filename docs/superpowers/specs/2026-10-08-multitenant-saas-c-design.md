## 1. 背景

既存システムは単一テナントの整骨院向けLINE予約Bot（GAS+スプレッドシート+LINE Messaging API+Stripe+Cloudflare Workers・本体JS約12,700行・E2Eテスト36本緑・1院のみで実運用品質）。GitHub棚卸し（2026-10-08）で最有力事業化候補と判定された。r1で単一基盤完全マルチテナント（案B）は「12,700行横断改修+静かな混線（院間データ混入）リスク」により見送り、「予約処理は複製・管理だけ中央集約」の案C（ハイブリッド型）を採用。

## 2. 案の定義と判断記録（ADR要約）

| 案 | 内容 | 判定 |
|---|---|---|
| A | 複製のみ手動運用（中央なし） | 工数最小だが語り・管理面が弱い。ロールバック先として保持 |
| B | 単一基盤完全マルチテナント（tenant_id全統合） | 見送り（混線リスク+週20h枠で非現実的・r3 OR1#6） |
| **C** | **本設計（複製+中央集約）** | **採用**（2026-10-08・N=3院到達時に再評価） |

詳細比較（中央を作る/作らない4軸・TCO表）はADRとして本specの実装時に `docs/adr/` へ展開する。

## 3. アーキテクチャ

- **データプレーン**: 院ごとにGAS複製+スプレッドシート複製+LINE Bot。現行コードを無変更で流用・E2E 36本を有効のまま維持
- **LINE webhook**: 各院GAS直受け（中央非依存）+署名検証。署名検証失敗時=401即返+ボディ空+テナント単位ログ（30日ローテート）+イベントID冪等キー（GAS Cache 24h・LINEリトライ暴走防止）
- **コントロールプレーン（中央）**: Cloudflare Workers+D1。テナント登録簿（tenant_id/院名/GASデプロイURL/LINE channel ID/Stripe契約ID/状態）+稼働監視+Stripe請求+オンボーディング
- D1: 日次エクスポート（RPO=24h・**失敗検知はC2で毎時ステータスチェック**）・RTO目標=4h+復元手順書+C3で復元訓練1回（失敗時代替=CSV→D1インポート）・Workers KV読取副本
- テナント状態遷移: (a)中央稼働前=自律稼働 (b)ライセンス有効=通常 (c)TTL72h超過=警告（予約継続） (d)7日超過=人手提供停止判断
- 個人情報: 中央登録簿は院名等の最小限のみ・予約データ（氏名・電話・来院履歴）は各院シートに閉じる（設計保証をアーティファクト化）
- シークレット: 各院GASのScript Properties（漏洩影響半径=1院）+編集者=開発者のみ+ローテーション手順+C2で半自動化（GAS API経由）
- 管理手段: 1〜3院ではWrangler CLI+定型操作手順書（フルUIは構築しない・N=3再評価事項）

## 4. 段階移行（軽量中央ハイブリッド順序・確定）

| フェーズ | 内容 | ゲート |

## 5. エラー処理・運用

- bounded fail-open（ライセンスキャッシュTTL=72h・超過で警告+通知・7日超過で人手停止判断・未入金×2回で自動停止）
- ハートビート: 実イベントベース+日次定期トリガー保証（C1で検証）
- fail条件: LINE API 5xx/timeout 5分以内5回→予約受付自動停止+緊急アラート+Bot障害告知。復旧=自動再試行（1/5/15分）→再疎通で自動復旧→30分超過で手動
- テナント側fail条件: Stripe webhook 24h不着→課金unknown化+手動確認・ハートビート24h不着→テナントunknown化・Properties欠損→起動拒否
- デプロイ: 深夜帯ルール+T0002先行適用→24h観察→本番+部分デプロイ検知（最終更新時刻pull差分）+バージョン照合ゲート化
- CC実装の品質担保: 各フェーズ=リグレッション実行+CIログ保存

## 7. リスク

- スケール閾値: オンボーディング30分/院超過またはGASクォータ逼迫（外挿=上界/平均2本立て）でB案移行再検討。**クォータ逼迫時の即時アクション=有料院1院で課金枠確保→他院無料β保留（消費率80%超で判定）**
- GAS無料枠縮小・LINE API破壊的変更（変更ログ監視のみ・抽象化レイヤーは無変更流用と矛盾で不導入・破壊的変更検知時=本設計の再評価）
- 反証シナリオ: ①中央2週ダウン→Workers復旧後D1-GAS差分レポート ②GAS無料枠縮小→課金枠確保アクション ③テナント側GAS障害→LINE標準応答メッセージで最低限維持
- 最悪ケース（GoogleアカウントBAN）: E2E・clasp設定・デプロイスクリプトのGitHub管理+各院Properties暗号化バックアップ（顧客合意付き）+スプレッドシート週次エクスポート+日次CSV匿名化を別事業者（R2等）へ+BAN Playbook（24h以内告知・返金・Stripe webhook停止時の自動課金停止+顧客連絡）

## 8. Phase 0（C0と並行実施可・C1着手前までに完了する測定・決定事項）

現行院メトリクス2〜4週（KPIベースライン）/GASクォータ消費率測定（webhookリトライ最悪値シナリオ含む）/適法性チェックリスト（Stripe名義・特商法・インボイス・兼業規定+ココナラ経路）/**兼業確認「明確OK」がC3課金開始の前提（順序保証）**/兼業NG時=無償β（撤退基準ルール同適用）+OSS化/T0001課金扱い決定/撤退基準（面談1件+往復2回=操作的定義・2週連続面談3件未達で撤退・自動カウント）/工数WBS（開発+営業6:4・0.5〜2h粒度・2週連続超過でスコープ縮小。落とす順序= C3ダッシュボード→監視拡張→C2並列テスト簡略化・A案ロールバックは最終手段）/スケール外挿方法の事前決定

## 9. KPI

予約成功率99%以上（分母=Bot受付リクエスト・システム起因失敗を除く）/ハートビート応答率99.5%以上+単一テナント連続欠落3回以下/検知遅延3h以内（超過継続=C3昇格保留+訓練追加）/課金処理KPI=失敗24h以内検知対処100%/設定取り違え0件（自己診断4項目全一致）/オンボーディング30分以下
