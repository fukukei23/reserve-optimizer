# QuickReport 改訂案 A″（multi-llm-review 統合結果）

- 当初目的: 整骨院クリニック側の日常運用負荷を最小化（毎朝5秒で日報完了）しつつ、経営最重要KPIである実際の来院数を確実に取得する
- レビュアー: Gemini 3.1 Pro (5件) + MiniMax M3 (9件)
- 両LLMが独立に指摘した致命点（直交性実証）: 来院数スケール・9時固定・差分ロジック・書込堅牢性

## 改訂案 A″（採用指摘を統合）

1. **来院数入力方式変更** [Gemini#1 critical / MiniMax#1 high / #8 low 両LLM一致]
   - QuickReply「0/1/2/3/4/5/6以上」→ **数字直接入力（リプライで「25」等）**
   - 理由: 整骨院の1日来院数は数十人規模。0〜6+では「6+」に丸まり実態不明＝KPI取得目的と矛盾
   - **「1タップ」sellは放棄・「5秒」sellは維持**（テンキー入力5秒）。バックログ記載「1タップで回答」は修正要
2. **送信タイミング変数化** [Gemini#4 med / MiniMax#2 high 両LLM一致]
   - 毎朝9:00固定 → **営業時間設定変数化 + 休診日ガード**（WORKING_DAYSマスタで営業フラグ判定）
   - 理由: 9:00は朝礼・営業開始直後と重なり通知埋もれ。休診日の空問いかけは無視バイアスの学習を生む
3. **カード簡素化** [MiniMax#6 med]
   - 「昨日◯件予約・来院数は？」ミニマル1行 + 数字入力。売上等の詳細数値は週次/月次レポートへ格下げ
   - 理由: 情報過多はタップ（入力）漏れ率を上げる
4. **差分指標の修正** [Gemini#2 high / MiniMax#3 high 両LLM一致]
   - 「実際の来院数 − Bot予約数」→ **「実際の来院数 − Bot経由来店完了数（_handleMarkVisited確定値）」**
   - 指標名はニュートラル（「電話/窓口経由来院数」「Bot消化率」）。「no-show率」の単独使用は誤読リスクで避ける
   - 理由: 単純差分では no-show と電話/窓口予約が相殺され実態を見誤る
5. **DAILY_REPORT 新規シート作成** [Gemini#3 high / 調停で採用]
   - 日付キーの行指向・append-only。WEEKLY_SUMMARY とは粒度を分離
   - 理由: 日次と週次の粒度混在はBI拡張時に破綻。行指向は月次集計・ダッシュボード化が容易
6. **堅牢性（フェイルセーフ＋冪等性）** [Gemini#5 med / MiniMax#5 med 両LLM一致]
   - 12:00時点で前日分未記録ならリマインド送信
   - postbackハンドラで LockService による重複防止 + 書込失敗時リトライ（冪等）
7. **管理者 LINE ID 集約** [MiniMax#7 med]
   - ScriptProperties で配列管理（院長+副主任等の複数管理者対応）。送信先0件時は生存監視用Webhookへダミー送信
